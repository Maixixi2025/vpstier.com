## 1. Rationale + Hot-Source

**Why this topic, and why today.** On **18 November 2026** the NGINX project shipped a security release fixing **nine** CVEs, five of which are remote code execution paths that a research team collectively named **NGINX2Root**. The headline flaw, **CVE-2026-123007** (memory corruption in HTTP/2 flow control), has been present in every official NGINX release since **1.9.5 in 2015** — eleven years — and needs only HTTP/2 to be enabled. NGINX powers more than **225 million websites**. For a VPS audience this is close to a worst case: NGINX is the default front door on every self-hosted box, and a budget VPS is exactly where a self-managed web stack lives.

**The story that is actually new (and the one no outlet wrote):** the bug does not stop at the web server. For a VPS buyer that changes the question from "should I patch my web server" to "does my box let a web-server compromise become a host compromise". Every container on that host shares the kernel.

## 3. H2 Chapter Plan (10 sections)

1. **What NGINX2Root actually is — and how many flaws it really is** — open with the vendor's own list, not the headlines. The 18-Nov release fixed **nine** CVEs; **five** are independent RCE paths (`CVE-2026-123007` HTTP/2 flow-control memory corruption; `CVE-2026-123633` HTTP/2 use-after-free; `CVE-2026-121810` HTTP/3 use-after-free; `CVE-2026-123634` resolver use-after-free; `CVE-2026-113425` mail-proxy use-after-free), plus `CVE-2026-118899` (TLS 1.3 infinite loop), `CVE-2026-120993` (PROXY protocol v2 NULL deref), `CVE-2026-120967` (SNI bypass) and `CVE-2026-125283` (alias+try_files buffer overflow). Give each a one-line plain-language description and the configuration it needs. Note that the vendor's own list carries 78 advisories total, **35 of them with 2026 CVEs** — the pace of disclosure itself is a story. Then the severity reconciliation, stated as two separate facts: the vendor labels 123007 **"major"** and 123633 **"medium"**, while the CNA scores all three of the HTTP/2/HTTP/3 trio at **CVSS 3.1 8.1 / CVSS 4.0 9.2**.
2. **CVE-2026-123007: the eleven-year-old bug** — the flagship, in plain language, from the CNA description and the Wiz technical deep dive. NGINX tracks how much response data it may send in a counter (`send_window`). When a stream is cancelled with data still queued, the unused allowance is refunded **without checking the protocol's maximum**; the client's own increase then pushes the counter past that maximum. The next bounds check subtracts the current allowance from the maximum using an **unsigned integer** — the subtraction wraps and underflows to a very large positive value, so the "is there room?" check now passes when there is not. The invalid counter eventually becomes a **negative length** in `ngx_http_v2_send_chain()`, producing an out-of-bounds copy in the TLS send path. Two facts that make this urgent and two that keep it honest: the code has been present since **1.9.5 (2015)** and the vendor confirms the vulnerable code was still in **master on 10 November 2026**; and the tested path was **HTTP/2 over TLS on 64-bit systems serving static files** — no backend application and no third-party module required.
3. **The other four RCEs — and which ones HTTP/2 does NOT block** — the part the coverage mostly gets wrong. Table of the five, with the exact configuration each needs: 123007 (HTTP/2 enabled); 123633 (HTTP/2 **plus** a request forwarded to a backend, and a worker low on `worker_connections`); 121810 (HTTP/3 plus a backend); 123634 (`resolver`, a request-derived `proxy_pass` destination, or `mirror` with `mirror_request_body off` — and note that other subrequest features such as SSI may reach the same bug); 113425 (mail proxy with `proxy on` and `auth_http`). Then the honest line: **disabling HTTP/2 blocks two of the five**. It does nothing for the resolver, HTTP/3 or mail-proxy paths. The resolver flaw alone reaches servers that never speak HTTP/2 at all.
4. **The 4-command exposure check — copy-paste, run it now** — the practical core, taken from the Xint method and written for a reader who has never opened a terminal. **Step 1, version:** `nginx -v` — `1.9.5` through `1.31.8` means the vulnerable code is present; `1.9.4` or earlier means HTTP/2 did not exist yet and you are unaffected; `1.31.9`+ or a backported build needs the package check from §5. **Step 2, module:** `nginx -V 2>&1 | grep -q -- '--with-http_v2_module'` — `HTTP2_MODULE=absent` means the vulnerable code is not in your binary at all. **Step 3, enabled:** `sudo nginx -T 2>&1 | sed 's/#.*//' | grep -nE 'listen[[:space:]].*http2|^[[:space:]]*http2[[:space:]]+on[[:space:]]*;'` — no output means HTTP/2 is not on. Add the caveat that `nginx -T` reads the config **on disk**, so an unreloaded change means the running config differs. **Step 4, reachable:** from a machine **outside** your network, `openssl s_client -connect {HOST}:443 -servername {HOST} -alpn h2 < /dev/null 2>&1 | grep -E 'ALPN protocol:|No ALPN negotiated|Connection refused|handshake failure'` — `ALPN protocol: h2` means the Internet can reach your HTTP/2. And the caveat that matters: **if a CDN or reverse proxy sits in front, this test only reaches the proxy** — run it directly against the origin too, because the vulnerability lives on the origin.
5. **The patch table — what "fixed" actually looks like on your distro** — the version-string trap up front, because it is the thing that catches people: **distros backport fixes without changing `nginx -v`**. Then the live distro status read this run. **Upstream:** 1.31.9 (mainline) and 1.30.7 (stable), both **18 Nov 2026**; NGINX Plus 37.3.0.1 / 37.2.0.1 / 37.0.8.1 / 37.0.7.1 per the CNA records. **Debian:** bookworm fixed in `1.22.1-9+deb12u11` (**DLA-4918-1**), trixie fixed in `1.26.3-3+deb13u11` (**DSA-6642-1**), sid fixed in `1.30.6-4`; forky still `1.30.6-3` vulnerable. **Ubuntu:** upstream pocket released in `1.31.9,1.30.7`; jammy `1.18.0-6ubuntu14.23`; noble `1.24.0-2ubuntu7.20`; resolute `1.28.3-2ubuntu1.13`; stonking `1.30.4-7ubuntu1.2`; xenial/focal/bionic via the ESM pocket; trusty **not affected** ("code not present" — 1.4.6 has no HTTP/2 and no flow control, per the Ubuntu maintainer note). **Red Hat:** RHEL 8/9/10 nginx packages still **Affected**, Bugzilla 2575895 / 2576209 both `urgent` with **no `cf_fixed_in`** — i.e. **no RHSA build was published as of 19 Nov 2026**. Give the actual commands (`apt-get update && apt-get install --only-upgrade nginx`, `dnf update nginx`, `nginx -t && systemctl reload nginx`) and the critical detail from the vendor: **a reload does not replace the running executable** — the service must be restarted or the binary live-upgraded, and you must confirm the old workers have exited.
6. **If you cannot patch today: the emergency mitigations, and what each one actually covers** — the honest mitigation matrix. **Disable HTTP/2** on the affected server blocks: `listen` without the `http2` parameter, plus `http2 off;` in the affected server blocks on NGINX 1.25.1 and later (the `http2` directive did not exist before 1.25.1, so on older builds the only lever is the `listen` parameter). Test app compatibility, restart, confirm old workers exited, re-enable after upgrading. **Block the SCTP module** on hosts that do not need it: `install sctp /bin/false` in a `.conf` file under `/etc/modprobe.d/` — with the two limitations stated plainly: this only stops loading **through modprobe** (it does not unload an already-loaded module) and does **not** disable SCTP compiled into the kernel. **Investigate for compromise** — and here is the detail no outlet led with: an attack using CVE-2026-123007 may leave **almost nothing in the access log**, because the `WINDOW_UPDATE` and `RST_STREAM` control frames that trigger it are not logged as requests and TLS encrypts them in transit. So the detection surface is elsewhere: run `sudo ss -tinp state established '( sport = :443 )'` twice a short interval apart and compare `bytes_received` and `bytes_sent` — the attack pattern is **one long-lived connection from the same external IP with `bytes_received` climbing fast while `bytes_sent` stays small**, alongside many short-lived TLS connections from that same IP. Add: unexpected NGINX worker crashes, and commands launched by NGINX workers — but state the vendor's own caveat that these are **general warning signs, not confirmed indicators**. Xint also says to check the NGINX binary and its modification time.
7. **The part no outlet wrote: the chain to host root** — the escalation step, and the reason a VPS reader should care more about this than a generic web-server CVE. Xint also found a **separate Linux kernel SCTP flaw** — a use-after-free or double-free in the SCTP send path, where a pending send's association can be transferred to another socket and then freed, **introduced in Linux v4.15 in 2018**. Chained with any of the five NGINX bugs, it turns "code execution as the nginx worker" into **root on the host** — demonstrated in their tests, **including from inside a Docker container to root on the underlying host**. The mechanism gives two primitives: a **kernel memory disclosure that defeats KASLR** and an **arbitrary function call in the kernel**. The honest boundary: **this kernel flaw carries no published CVE id in the write-up**, so it cannot be looked up or tracked yet, and no kernel fix is referenced. The practical consequence: on a VPS where the SCTP module is loaded and reachable, a web-server compromise is a host compromise. Also note that on many distributions the SCTP module **is installed by default and the kernel auto-loads it the first time a program opens an SCTP socket** — so "I don't use SCTP" is not the same as "SCTP is not loaded".
8. **What this means for the VPS decision itself** — the vpstier-specific angle, and the honest version of it. The responsibility split is the story: **on shared hosting the provider patches the web server; on a VPS you own it**, and this is a case where the gap is not theoretical — the vulnerable code shipped in **1.9.5 and sat in upstream master for eleven years**, and the NGINX advisory list now carries 35 CVEs from 2026 alone. That is not a failure of your configuration; it is what an unmanaged software stack looks like. Two practical selection criteria fall out of it: (a) **does the provider let you run the web server yourself, so you can patch it on your own schedule**, and (b) **does the provider's stack keep a web server in front of you that you cannot patch** — a CDN or managed-proxy front end is a mitigation for §4 but also a place where you cannot see or fix the origin. Then the honest affiliate framing, which is unusually clean here: **RackNerd is not the fix, it is the box you patch.** Full root, KVM, your own distro, your own `apt upgrade nginx`, and a host you can reboot. Live figures read this run: **from $2.24/mo**, and the specials ladder **1 GB $15.98/yr**, **2.5 GB $27.98/yr**, **4 GB $47.98/yr**, **6 GB $74.98/yr**, **8 GB $94.98/yr** — all KVM, 1 Gbps port, 1 IPv4, full root, provisioned immediately. Say the trade-off honestly: a $15.98/yr box is where you will run a public NGINX, and it is *your* job to patch it.
9. **The wider 2026 pattern — and what to actually take from it** — place this in context without turning the piece into filler. Three honest observations. (a) **The disclosure cadence**: the NGINX advisory list carried 2 CVEs in 2025 and **35 so far in 2026** — a step change, and Xint attributes part of it to AI-assisted research (their fully automated scan found four of the five with no human guidance; the fifth was found by a human researcher preparing for a conference). (b) **The eleven-year dormancy**: a project with one of the most scrutinised codebases in the industry carried a memory-corruption bug for a decade. The lesson is not "NGINX is bad" — it is that **an unpatched service is unpatched regardless of how famous its maintainer is**. (c) **The ASLR point, stated plainly**: every one of these advisories says code execution "can" happen when ASLR is disabled or bypassed. ASLR is your last line, not your first — and on a cheap VPS there is no security boundary between "code as the nginx worker" and "code on the box" beyond the module you never loaded.
10. **The 90-minute response plan, in order** — the close, as a numbered sequence the reader can run tonight. (1) Run the four checks from §4 and write down the result — **know whether you are exposed before you do anything else**. (2) If you are exposed and can patch: `apt-get update && apt-get install --only-upgrade nginx` (or the dnf equivalent), then `nginx -t`, then **restart the service** — not just reload — and confirm the old workers exited. (3) If you cannot patch tonight: disable HTTP/2 and restart, and block the SCTP module with `install sctp /bin/false`. ## 4. FAQ (5 questions)

1. **Am I actually at risk, or is this another CVE that only hits giant setups?** It is a broad one. The flagship bug needs only HTTP/2 enabled, and the vulnerable code shipped in **every official release from 1.9.5 (2015) through 1.31.8** — it was still in upstream `master` on 10 November 2026. NGINX powers more than 225 million websites and is the default front door on self-hosted boxes. A small VPS running a public site is squarely in the exposed population.
2. **Does turning off HTTP/2 protect me?** It protects you from **two of the five** RCE paths (`CVE-2026-123007` and `CVE-2026-123633`), and only if the module is actually disabled — including the `http2` parameter on `listen` directives. It does **not** block the resolver use-after-free, the HTTP/3 use-after-free or the mail-proxy use-after-free, and it does nothing for the TLS 1.3 infinite loop, the PROXY-protocol NULL deref, the SNI bypass or the alias+`try_files` buffer overflow. It is a mitigation to buy time, not a fix.
3. **Is this being exploited in the wild right now?** No confirmed exploitation was found for this run. None of the five CVEs appears in the CISA Known Exploited Vulnerabilities catalog (checked against the live feed, 1,786 entries), and Wiz Research states it is **not releasing its proof-of-concept exploits** at this time. That is not the same as saying it cannot happen: the code is public, the fix is public, and the disclosure is public.
4. **I run Docker on my VPS. Is a container enough isolation?** No, not on its own. The research team chained the web-server RCE with a **separate Linux kernel SCTP flaw** and **escaped a Docker container to root on the underlying host**. Containers share the host kernel, so a kernel-level bug defeats the container boundary. The SCTP flaw has **no published CVE id** yet, so you cannot track it — which is why blocking the module (`install sctp /bin/false`) is the only defence available right now.
5. **My provider says they handle updates. Am I still responsible?** On a VPS, yes. A provider can patch the host's base OS and the hypervisor; **your** NGINX, in your own VM, on your own configuration, is yours to update. This one is a good example of why: the advisory list shows **35 CVEs from 2026 alone** and a flagship bug that went unnoticed for eleven years — the provider's OS patching does nothing for a web server you installed from a script three years ago.
